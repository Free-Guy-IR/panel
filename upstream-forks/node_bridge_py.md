## Behaviour changes the panel takes with this bridge pin (not read by the gate)

What changes for the panel when its pin moves from 5b21adc6b961 (`0.10.0+singbox.1`) to 3eb396cbfb0f
(`0.11.2+singbox.1`). Measured on 2026-11-23 on macOS with CPython 3.14.7 and 3.12.14 and OpenSSL 3.5.7, against the
panel's integration head 0b3f5b8a8; not measured on Linux, and not seen in production.

- A gRPC call that fails certificate verification now raises NodeAPIError code -2 with a detail such as `Certificate untrusted issuer: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer certificate`, where 0.10.0 raised code 0 with the bare SSL message: #35 added an `ssl.SSLCertVerificationError` branch to `_handle_error` (`PasarGuardNodeBridge/grpclib.py:320-321` on 3eb396cbfb0f). The panel's health check reconnects a BROKEN node only when `should_reconnect_after_health_error` is true, which needs `error_code > -1` (app/jobs/node_checker.py:219-228 and :457 on 0b3f5b8a8). Measured by running the panel's real `process_node_health_check` twice on an in-memory SQLite node row, with the fixtures of tests/test_node_health_usage_collection.py, `connect_single_node` and the notifications replaced by recorders, against a real bridge gRPC node whose TLS server presents a certificate its `server_ca` does not trust: with 5b21adc6b961 both probes ended with the node in error and code 0, and each called `connect_single_node`; with 3eb396cbfb0f both probes ran and ended with the node in error and the `Certificate untrusted issuer` message, and neither called `connect_single_node`. So the health check no longer reconnects such a node after every failed probe; it leaves it in error. Code 0 and -2 both count as an unanswered probe for the probe backoff (node_checker.py:316, read from the code). Over REST the same probe made no reconnect with either bridge: 0.10.0 reported a connection error, 0.11.2 the same -2 detail.
- PasarGuardNodeBridge/tls.py on fork main is upstream v0.11.2's tls.py plus one line from 3eb396cbfb0f, `ctx.verify_flags |= ssl.VERIFY_X509_PARTIAL_CHAIN`, in `TLSPolicy.context` for PEM and system trust (`git diff --numstat` from upstream tag v0.11.2 to fork main on tls.py: 1 added, 0 removed). The pinned-fingerprint context, which does its own check, is unchanged.
- With that line, on Python 3.12 a PEM `server_ca` bundle of two self-signed certificates with the same subject and no authority key identifier, as in a certificate rotation, verifies a node presenting either of them, and so does system trust that holds such certificates; a leaf whose issuing CA is absent is trusted when the leaf itself is in the bundle. CPython 3.12's create_default_context does not set VERIFY_X509_PARTIAL_CHAIN, and before the line only one of the two certificates verified: the bridge's RED commit 0cbc23096274 fails 24 subtests of tests/test_tls_trust_anchors.py on 3.12.14 and 3eb396cbfb0f passes them all, and bridge 0.10.0, which builds the same create_default_context with `cadata=server_ca`, refused the first certificate of such a bundle and accepted the second in 6 runs out of 6 on 3.12.14. The panel needs Python 3.14 (`requires-python = ">=3.14"`, image python:3.14-slim-bookworm), and from CPython 3.13 create_default_context sets VERIFY_X509_PARTIAL_CHAIN and VERIFY_X509_STRICT itself (Lib/ssl.py), so there the line changes nothing: on 3.14.7 the context's verify_flags are equal before and after it, 0.10.0 already accepted both certificates of the bundle, and the RED commit fails only the subtests that clear the flag to imitate 3.12. The bridge's CI passed its tests, the trust-anchor tests included, on ubuntu-latest and windows-latest with Python 3.12 and 3.14 at 3eb396cbfb0f; the RED commit was not run on Linux.
