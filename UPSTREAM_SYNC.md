# Upstream Sync Ledger

This file records every upstream PasarGuard commit that this fork has not cherry-picked
but has dealt with anyway. The upstream parity gate in `.github/workflows/upstream-inventory.yml`
reads it through `scripts/upstream_inventory.py --fail-on-unported UPSTREAM_SYNC.md` and fails when
an upstream commit past the pinned baseline, on any upstream branch or tag, is neither ported
nor listed here.

A commit ported with `git cherry-pick -x` needs no entry: the `(cherry picked from commit <sha>)`
trailer in the fork history covers it automatically while the lines it adds are in the fork and the
lines it removes are gone, and so does any rebased or duplicated copy of a covered commit with the same
`git patch-id --verbatim`. An upstream merge commit whose conflict resolution changes files (a
non-empty `git show --remerge-diff`) needs a decision like any other commit.

Everything else goes under one of the three headings below, one list item per commit:

    - `<sha>` <reason>

Use the full 40-character sha. A prefix of at least 9 hex characters is accepted while it names
exactly one upstream commit in range, but it becomes a ledger error once that commit leaves the
range. An entry without a reason fails the gate.

`Ported by design` is for upstream changes the fork carries in a different form (adapted by hand,
merged into a fork commit, or superseded by fork code). `Waived` is for upstream changes the fork
deliberately does not take. `Port queue` is for upstream changes the fork has decided to take but does
not carry yet: each entry needs `until: YYYY-MM-DD` no more than 30 days ahead and a `security: yes` or
`security: no` classification with a reason, the gate lists it as an owed port and says the fork is not at
parity, and the day after the deadline the gate fails unless the commit was ported (a `cherry-pick -x`
trailer or a patch-identical copy of a ported commit, which the gate then reports as ready to delete from
the queue) or decided again.

Every port-queue entry must carry `security: yes` or `security: no`. A missing classification fails the
gate at once, so the dangerous direction fails closed. `security: yes` means the commit is security-relevant
and gets no grace: while it is unported and has no `Ported by design` or `Waived` decision, the gate fails
immediately whatever its `until:` date; its queue line stays as the record of the decision to port it, and
the gate turns green when the port lands. Classify `security: yes` when the commit changes authentication,
authorization, API-key, token, session, JWT, passkey or credential handling, or input injection, escaping
or sanitizing, or when the upstream commit, pull request or release is titled or labelled a security or
CVE/GHSA fix; otherwise `security: no` with a reason. The keyword set (security, CVE/GHSA, vulnerability,
auth, API key, JWT, passkey, WebAuthn, credential, injection, XSS/CSRF/SSRF, escaping, sanitizing,
traversal, bypass, spoof, hijack, disclosure, RCE, and a `(security)`/`[security]` mark) is only a hint: it
never classifies on its own, but when a `security: no` entry matches it the gate prints a re-review note so
a human confirms the `no`.

A `security: yes` port-queue entry, a `security: yes` `Waived` entry and a bridge or npm waiver with
`security = "yes"` are accepted only under exactly one owner decision recorded under `## Owner decisions` and named
as `owner-decision: YYYY-MM-DD-<name>` (`owner_decision` in the TOML files). The record needs a reason, the full
shas of the upstream commits (or the `package@version` of the waivers) it covers, and one `until:` at most 30 days
after its date; it may not be dated after the day the gate runs. The decision must still be running, the entry
must be one the record lists, and a dated entry may not outlast the record, so an undated security waiver ends
with its decision. An entry naming a decision that is missing, ended, malformed or does not list it is unported
and a ledger error, a port-queue security entry without a decision still gets no grace, and an `owner-decision:`
on any other entry is refused. A port-queue entry classified `security: no` says why, as `security: no, <reason>`;
the gate counts the ones that do not.

`Waived` entries need the same `security: yes` or `security: no` classification. A waived `security: yes`
entry also needs a recorded owner decision, as above; without it the gate fails, so a security fix is never
waived silently. A `Ported by design`
entry needs the classification only when its reason or the upstream commit subject matches the keyword hint.
In every section, an entry classified `security: no` whose upstream subject or reason names a CVE or GHSA id
or carries a `(security)` or `[security]` mark fails the gate: classify it `security: yes`. The bridge and npm
waiver files follow the same rule with `security = "yes"` or `security = "no"` and, for `yes`, a recorded
`owner_decision = "YYYY-MM-DD-<name>"` that lists the waived `package@version`.

The baseline in `.upstream-baseline` is trusted only when it is a grandfathered release: today v5.4.1
b56ffe369f54, passed to the gate as `--grandfathered-base` in the workflow. A newer baseline does not shrink
the checked range: the gate then checks every upstream commit from the newest grandfathered release below it,
and each one must be ported by content (a merge or a pick whose added lines are all in the fork and whose
removed lines are all gone) or decided here. Ancestry alone never proves a port, because an `-s ours` merge, a
merge that is reverted later or a squashed sync that dropped a hunk all make upstream commits reachable while
their lines are missing. A baseline that descends from no grandfathered release stops the gate with an error.

Known limit: the gate tells a final upstream release from a pre-release by its tag name (PEP 440, or an `rc`,
`beta`, `alpha`, `pre`, `preview` or `dev` part), not by the GitHub release flag, so it needs no network. A
final GitHub release cut on an rc-named tag would be read as a pre-release; all 63 upstream panel tags of
2026-10-25 follow the naming convention.

A reason that contains `until: YYYY-MM-DD` covers its commit only up to that date, and the date may be at
most 30 days ahead, so every dated decision is looked at again within a month. After it the gate fails and the
commit needs a new decision. Pending upstream feature branches are recorded this way.

A `Waived` reason that starts with `UNMERGED-WIP` or `pending` is also conditional on upstream: it covers
the commit only while upstream keeps it off its release lines (upstream/main, upstream/dev and every
upstream tag). When upstream merges that commit, or a rebased copy of it with the same patch-id, the gate
fails at once, whatever the `until:` date says, and the commit needs a new decision. Any other `Waived`
reason is permanent and also covers rebased copies.

The gate also reads `.upstream-refs`, the snapshot of every upstream branch and tag head the fork
has reviewed. It fails while a live upstream head is missing from the snapshot, and it keeps
tracking the commits of every recorded head after upstream deletes or force-pushes the branch.
After reviewing new upstream heads, record them with
`python scripts/upstream_inventory.py --base <baseline tag> --track 'refs/remotes/upstream/*' --track 'refs/upstream-tags/*' --fail-on-unported UPSTREAM_SYNC.md --refs-snapshot .upstream-refs --write-refs-snapshot`.
